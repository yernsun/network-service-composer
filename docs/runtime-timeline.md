# Runtime timeline

The real Controller timeline at `/infrastructure/events` combines persisted deployment operations with Docker events collected after this feature is enabled. Existing deployment and scale operations remain available under `/operations/{id}` and appear immediately after migration. Docker events from before collection began are not reconstructed. An old scale operation without a recorded target replica count shows its recorded action and outcome only; the current replica count is not substituted.

`GET /api/v1/timeline` returns newest records first with a time and ID cursor. It accepts `project_id`, `environment_id`, `runtime_id`, `application_id`, `service_id`, and `category` filters. The response includes `coverage.state`, per-source collection state, and `retained_from`. Empty results mean no matching recorded items only when collection coverage is established. An unavailable or partial source is shown separately, including a node that has not been configured or whose heartbeat is stale.

The Controller stores only allowlisted Docker identity, timestamps, action, task/container state, exit code, and OOM evidence. It does not store raw Docker attributes or infer that a failed instance recovered. Application operations snapshot their project and environment when created. Older operations use a currently existing application/environment link; those without a resolvable link remain visible only in the global view with an unknown scope.

## Rollout

1. Back up the Controller database through the normal operational procedure, then run the new binary's `nsc-controller migrate --config /etc/nsc/config.yaml` against that database before upgrading any serving Controller instance. Confirm migration `00012_runtime_events` completed.
2. Upgrade all Controller instances that share the database. The direct Runtime watcher records Compose container and Swarm service events. Complete Swarm task inventory observations also record task creation, state changes and disappearance, since Docker's manager event stream may omit task replacement events. The first task observation establishes a baseline rather than reconstructing the past. In a multi-node cluster, each provisioned Controller node also watches its local Docker Engine and sends bounded event batches over the existing mutual-TLS internal listener. The receiving Controller checks the node certificate binding and the current database session owner before acknowledging a batch. A retry is deduplicated by event identity.
3. Configure a Controller collector binding for **each** Swarm node and verify `/api/v1/timeline?runtime_id=<runtime-id>` reports every node as collecting. A missing binding is reported as `collector_not_configured`; a configured collector that has not started is `collector_not_started`. Do not treat manager service/task events as proof that worker container events are covered.
4. Inspect the current project/environment view and the global view. Check that historical operations appear and that new container exit, OOM, health, and Swarm task/service changes arrive with their source and object IDs. Test changes only in an isolated environment.

`controller.runtime_events.enabled` defaults to `true`. `controller.runtime_events.retention` defaults to `2160h` (90 days), and `NSC_CONTROLLER__RUNTIME_EVENTS__RETENTION` overrides it. The existing operation retention behavior is unchanged. Source start time, heartbeat, disconnection, and buffer overflow are retained as coverage evidence; a reconnect may replay events but cannot prove a disconnected interval complete. The global maintenance lease prunes runtime events after the configured retention period.
